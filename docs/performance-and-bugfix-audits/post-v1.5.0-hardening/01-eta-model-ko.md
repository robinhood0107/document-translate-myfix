# 예상 시간 모델 — 설계와 실측 검증

관련 코드: [`modules/utils/stage_sweep_eta.py`](../../../modules/utils/stage_sweep_eta.py),
[`modules/utils/automatic_progress.py`](../../../modules/utils/automatic_progress.py),
[`app/ui/pipeline_status_panel.py`](../../../app/ui/pipeline_status_panel.py)

## 모델의 기본 형태

파이프라인은 단계 배치다. 전체 페이지를 한 단계씩 통과시킨다.

```
detect-all → ocr-all → translate-all → inpaint-all → render-all → save-and-finish
```

추정기는 **(단계 × 페이지) 칸**을 단위로 본다. 남은 시간은 단계별로
`남은 페이지 수 × 그 단계의 페이지당 초` 를 더하고, 아직 시작하지 않은 단계에는 기동
비용(컨테이너 기동·모델 적재)을 더한다.

페이지당 속도는 **두 번째 페이지부터** 측정한다. 단계의 첫 보고까지의 간격에는 페이지와
무관한 고정 비용이 섞여 있고, 그것을 페이지당으로 환산하면 남은 시간이 크게 튄다.
그 간격은 대신 그 단계의 기동 비용으로 잡는다(#283).

## 융합 단계

렌더는 독립 단계가 아니다. 페이지의 인페인팅이 끝나는 즉시 전용
`QtRenderPool(max_workers=1)` 에 제출되고, `_render_all` 은 회수만 한다(#272). 실측으로
렌더는 창 0.0분에 작업 2.2분 — **완전히 인페인팅 뒤에 가려져 있다**(#287).

따라서 `render-all` 은 `FUSED_STAGES` 로 표시하고 **남은 시간에 더하지 않는다.**
목록에는 계속 띄우되 `인페인팅에 포함` 으로 표기한다. 파이프라인 전체가 보여야
지금 어디쯤인지 알 수 있기 때문이다.

## 무엇이 고장나 있었나

증상은 인페인팅 47장부터 327장까지 **280장이 처리되는 동안 남은 시간이 11~12분에 못
박혀** 있던 것이다. 원인이 셋 겹쳐 있었다.

### 1. 교대 보고가 상대 단계를 완료로 만들었다

단계가 바뀌면 직전 단계를 전체 완료로 표시하고 있었다. 융합 파이프라인에서는 인페인팅과
렌더가 **교대로** 보고한다. 첫 렌더 보고 하나에 인페인팅이 366/366 으로 찍히면서 모델이
통째로 망가졌다.

이제 `observe()` 는 단계 전환을 완료 신호로 쓰지 않는다. 완료는 그 단계 자신의
`pages_done` 이 `page_total` 에 닿을 때만 표시한다.

### 2. 융합 단계가 남은 시간을 두 배로 만들었다

융합된 렌더는 감싸는 단계의 페이스로 진행하므로 페이지당 속도가 인페인팅과 **같게**
측정된다. 그걸 합산하면 남은 시간이 정확히 두 배가 된다. 90/100 지점에서 36초가 남았는데
72초로 나왔다.

### 3. `remaining_seconds()` 가 단계 순서에 의존했다

순서를 벗어난 보고에서 어긋났다. 순서 무관하게 각 단계의 남은 칸만 세도록 바꿨다.

## 실측 검증 — 실제 45.8분 실행 재생

`logs/runs/run_2026-08-09_22-30-12.json` 을 그대로 재생했다.

| 시점 | 예상 남음 | 실제 남음 | 오차 |
| --- | --- | --- | --- |
| detect 366/366 | 8:45 | 44:57 | **−36분** |
| translate 92/366 | 38:26 | 37:33 | +53초 |
| inpaint 275/366 | 6:29 | 5:23 | +66초 |

**진행 중 오차가 커지지 않고 +53~66초에 고정된다** — 실행의 2.4%. "11~12분에 못 박힘"은
사라졌고 남은 시간은 단조 감소한다. 전체 예측 46:52 대 실제 45:47.

남은 상수 오차 +66초는 `save-and-finish` 의 사전 비중 0.2 이다. 실제로는 리포트에
잡히지도 않는 크기다.

## 초반 −36분은 왜인가

아직 시작하지 않은 단계는 **사전 비중표**로 추정한다. 그 표가 실제와 다르다.

| 단계 | 사전 비중 | 실측 비율 |
| --- | --- | --- |
| detect | 1.0 | 1.0 |
| ocr | 1.0 | **2.8** |
| translate | 3.0 | **25.2** |
| inpaint | 6.6 | **28.1** |
| save | 0.2 | **≈0** |

검출 대비 번역이 25배인데 3배로 잡으니 초반 3분 구간에서 5배 과소평가한다.

## 기계적 예측을 검토하고 채택하지 않은 이유

측정 비율 외삽 대신 **결정적 비용 모델**을 쓸 수 있는지 검토했다. 결론은 **현재 데이터로
정당화되는 변경이 없다**는 것이다. 검토 과정을 남긴다.

### 단위 비용은 실제로 안정적이다

유효 실행 2건(계측 버그 실행 제외)의 변동계수:

| 단계 | s/page | s/block |
| --- | --- | --- |
| detect | 5.4% | 5.4% |
| ocr | 4.4% | 4.4% |
| translate | 9.6% | 9.6% |
| **inpaint** | **0.2%** | **0.2%** |

인페인팅은 사실상 결정적이다. 단위 비용 모델 자체는 성립한다.

### 블록 기반 모델을 채택하지 않은 이유

`s/page` 와 `s/block` 의 변동계수가 **완전히 동일하다.** 이 작품은 페이지당 블록 수가
3.1로 거의 일정해서(366장에 1136~1142 블록) 두 지표가 구분되지 않는다.

즉 **이 데이터만으로는 블록 기반이 페이지 기반보다 낫다고 말할 수 없다.** 블록 밀도가
다른 작품 리포트가 쌓여야 갈린다. 근거 없이 복잡한 모델을 넣으면 검증할 수 없다.

### 절대값 대 비율 — 교차 예측

`seed_from_history` 는 이전 실행의 **절대** 페이지당 속도를 받아놓고 `rate / reference` 로
**비율로 변환한다.** 그래서 아직 시작하지 않은 단계는 이번 실행의 다른 단계 속도에
앵커링된다.

두 실행을 서로 예측시켜 비교했다(검출만 실측된 상태 가정).

| 단계 | 절대값 방식 | 비율 방식 |
| --- | --- | --- |
| OCR | 8.4% / 9.1% | 17.7% / 21.5% |
| 번역 | 21.1% / 17.4% | 8.8% / 8.1% |
| 인페인팅 | **0.4% / 0.4%** | 9.8% / 10.9% |
| 평균 절대 오차 | **9.5%** | 12.8% |

절대값이 평균적으로 낫고, 특히 인페인팅에서 압도적이다. 원리도 그쪽이 맞다 — 검출과
인페인팅은 GPU, OCR 은 VLM 컨테이너, 번역은 LLM 으로 **병목이 서로 다르고 함께 움직인다는
근거가 없다.**

이전 실행 하나만 있으면 시작 직후 전체 예측이 **±9%(약 ±4분)** 까지 좁혀진다.

```
2026-08-09_20-45   예측 45.8분  실제 42.1분   +8.8%
2026-08-09_22-30   예측 42.1분  실제 45.8분   −8.1%
```

### 그런데도 지금 바꾸지 않는 이유

세 가지다.

**표본이 2건이다.** 번역만 비율 방식이 나은데, 두 실행이 함께 느려진 것이 공통 부하인지
우연인지 구분할 수 없다. 단계별로 방식을 달리 고르는 것은 표본 2건에 대한 과적합이다.

**틀리는 구간이 짧다.** −36분 오차가 나타나는 것은 검출·OCR 이 도는 **초반 3분**뿐이다.
전체 45분 중 사용자가 그 값을 보는 시간이 가장 짧은 구간이고, 번역이 시작되는 순간
오차가 2.4%로 떨어진다.

**번역은 어느 방식으로도 ±20%다.** 내용과 LLM 부하에 좌우되는 실제 변동이라 모델로 줄일
수 없다. 번역이 전체의 절반을 넘으므로 이것이 정확도의 실질적 상한이다.

정확도를 더 올리려면 실행 리포트를 더 모아야 한다. 그때 판단할 항목:

1. `seed_from_history` 의 비율 변환을 제거하고 절대 s/page 를 직접 주입
2. 이력 없는 단계에만 사전 비중을 쓰고, 그 표도 실측값으로 교정
3. `save-and-finish` 사전 비중 0.2 → ≈0
4. 번역 진행 중 `eta_confidence` 하향
5. 블록 밀도가 다른 작품이 쌓이면 블록 기반 모델 재검토

## UI

파이프라인 상태 패널의 행 구성:

```
서비스 / 진행률 / 파일 / 예상 남은 시간 / 전체 예상 시간 / 경과 시간 / 예상 완료 시각 / Message
```

**전체 예상 시간**은 `경과 + 남음` 이다. 남은 시간을 알 수 없으면 전체도 표시하지 않는다.

네 시간 라벨에 마우스를 올리면 단계별 예상이 목록으로 뜬다. 툴팁에만 두는 이유는 평상시
패널을 넓히지 않기 위해서다.

```
단계별 남은 시간
  텍스트 영역 검출              완료  366/366
  텍스트 인식(OCR)            완료  366/366
  번역               00:09:38  200/366
  원본 텍스트 제거(인페인팅)  00:21:52  0/366
  번역문 렌더링          인페인팅에 포함  0/366
  저장 및 마무리         00:00:40  0/366
```

**완료된 단계와 융합 단계도 목록에 남긴다.** 남은 것만 보여주면 지금 파이프라인 어디쯤인지가
오히려 흐려진다. 0초라고 빼지도 않는다.

`remaining_by_stage()` 는 모든 단계를 `{stage, seconds, state, counted, pages_done,
page_total}` 로 돌려주며 `state` 는 `done / running / pending / fused / unknown` 이다.
`counted` 가 참인 행의 합은 `remaining_seconds()` 와 일치하고, 그 항등식을 테스트로
고정했다.

## 학습값 폐기

QSettings 의 학습 속도·기동 비용 그룹을 `_v2` 로 올렸다. 위 결함들이 살아 있는 동안
기록된 값은 오염돼 있고, 그대로 씨앗으로 쓰면 고친 모델이 틀린 값으로 시작한다.
