# v1.5.0 이후 안정화 감사

v1.5.0 승격(#277, 2026-08-06) 직후부터 관리형 런타임·단계 배치 파이프라인·시리즈
워크스페이스에서 연달아 드러난 결함을 정리한 기록이다. 이 감사가 다루는 범위는
PR #278부터 #288까지이며, 전부 `develop`에 병합됐다.

이 감사의 출발점은 하나의 증상이었다. **관리형 런타임이 전혀 뜨지 않았다.** 그것을
따라가면서 준비 스크립트의 개행 결함, 배치의 메모리 고갈, 출력 페이지 손실, 쓸모없는
계측, 예상 시간 모델의 구조적 오류가 차례로 드러났다. 각 항목은 서로 다른 원인이지만
같은 이유로 오래 살아남았다 — **측정되지 않았기 때문이다.**

## 이 감사가 세운 원칙

작업 중 반복해서 적용한 판단 기준을 남긴다. 이후 같은 영역을 건드릴 때 근거가 된다.

**측정되지 않은 것은 개선하지 않는다.**
렌더 스윕이 2.31초/페이지로 보였던 것은 계측이 워커 시간과 큐 대기와 tail drain을 한
바구니에 담았기 때문이다(#285). 실제는 0.370초/페이지였고 인페인팅 뒤에 완전히
가려져 있었다. 계측을 고치기 전에 손댔다면 없는 병목을 최적화했을 것이다.

**출력 개수는 입력 개수와 같아야 한다.**
단계 실패가 페이지를 조용히 삭제할 수 있었다(#282). 366장을 넣고 347장이 나왔는데
사유도 남지 않았다. 이제 배치 완료 직전에 디스크를 확인하는 조정 패스가 돌고,
쓰지 못한 페이지가 있으면 조용히 끝내지 않고 리포트에 개수와 파일명을 남긴다.

**메모리는 상한을 걸지 않고 임시본만 줄인다.**
4K 페이지에서 23.7 MiB 할당이 실패한 것은 하나의 연산이 커서가 아니라 프로세스가
이미 한계였기 때문이다(#282). 페이지 크기 제한을 두는 대신 float64 승격과 미해제
버퍼를 없앴다. 어떤 이미지든 처리한다는 요구를 상한으로 타협하지 않는다.

**품질을 움직이는 값은 근거 없이 건드리지 않는다.**
번역은 페이지당 2.77초로 가장 비싸지만 sampler·chunk·동시성을 손대지 않았다(#285).
그 값들은 출력 품질을 바꾸고, 그 브랜치에는 품질에 대한 증거가 없었다. 대신
`inference_and_cache`와 `dictionary_and_sanitizer`로 쪼개 어디에 시간이 있는지부터
드러냈다.

**정정은 기록한다.**
마스크 생성을 CPU 작업이라고 판단했다가 틀렸다(#287). CTD refiner는 CUDA에서 돈다
(`ctd_refiner.py:671`). 잘못된 전제 위에 세운 오프로딩 계획을 폐기하고, 실제 CPU
구간인 `cleanup_and_composite`만 대상으로 다시 잡았다.

## 남은 작업

- **인페인팅 cleanup 오프로딩** — 순수 함수 추출과 바이트 동일성 테스트까지 완료
  (#287). 파이프라인 스레드 밖으로 옮기는 일은 마스크 외부 침범 가드와 체크포인트
  기록을 함께 이동해야 해서 별도 변경으로 남겼다. 상한 효과는 42분 실행 중 약 5.8분.
- **블록 수 기반 비용 모델** — 현재 데이터로는 페이지 기반보다 낫다는 증거가 없다.
  근거는 [01-eta-model-ko.md](01-eta-model-ko.md#블록-기반-모델을-채택하지-않은-이유).

## 원자료 위치

실행 리포트와 앱 로그는 저장소 안 `logs/`에 쌓이며 추적되지 않는다(#286).

```
<repo>/logs/
├─ comic-translate.log     앱 로그, 8 MiB 회전, 5개 보관
├─ memlog_*.jsonl          메모리 진단
└─ runs/                   배치별 실행 리포트 (.txt / .json)
```

이 문서의 수치는 전부 `logs/runs/`의 실측 리포트에서 나왔다. 이미지·원문·좌표·raw
응답은 여기에 남기지 않으며, 저장소 정책에 따라 비추적 검증 보관소에만 둔다.
